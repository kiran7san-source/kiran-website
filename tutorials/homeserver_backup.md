## 1. Backup Architecture

The homeserver uses a **two-stage backup strategy**:

```text
HOMESERVER
    │
    │ Daily automated backup
    ▼
/mnt/cloud/homeserverbkp
    │
    │ Manual rsync
    ▼
External HDD
/mnt/backup-inspect
```

The first backup point is `/mnt/cloud/homeserverbkp`.

This contains:

```text
/mnt/cloud/homeserverbkp/
├── restic/
├── staging/
└── logs/
```

### Important distinction

The Restic repository contains the actual backup data.

The `staging` directory contains temporary/exported data generated by the backup script, particularly database dumps.

The `logs` directory contains backup execution logs.

# 3. Databases — Important

The homeserver does **not** rely on simply backing up live PostgreSQL/MariaDB data directories.

Instead, the production script performs logical database dumps.

This is important because database dumps are much safer for disaster recovery than blindly copying a live database directory.

The database dumps have been tested.

### Immich dump test

Verified with:

```bash
sudo docker exec immich_postgres \
  pg_restore --list /tmp/immich-test.dump
```

```text
PostgreSQL custom database dump
Format: CUSTOM
```

It contained 518 TOC entries and the required Immich extensions.

### BookOrbit dump test

```bash
  pg_restore --list /tmp/bookorbit-restore-test.dump
```

The dump was successfully recognized as a PostgreSQL custom dump containing 1,153 TOC entries.

### Seafile dump test

```text
ccnet_db

```

Therefore all three database backups have successfully passed basic restoration-format validation.

# 11. External HDD Backup

The external HDD is mounted at:

```text
/mnt/backup-inspect
```

The external disk should receive a copy of:

```text
/mnt/cloud/homeserverbkp/
```

### Recommended command

First verify the destination:

```bash
sudo ls -lah /mnt/backup-inspect
```

Then:

```bash
sudo rsync -aHAX --delete \
  /mnt/cloud/homeserverbkp/ \
  /mnt/backup-inspect/homeserverbkp/
```

### IMPORTANT

`--delete` makes the external copy mirror the source.

Therefore **always verify that `/mnt/backup-inspect` is actually mounted before running it.**

Check:

```bash
findmnt /mnt/backup-inspect
```

Also:

```bash
df -h /mnt/backup-inspect
```

If the disk is not mounted, **DO NOT run the rsync command**.

A safer version is:

```bash
mountpoint -q /mnt/backup-inspect || {
    echo "ERROR: /mnt/backup-inspect is not mounted"
    exit 1
}

sudo rsync -aHAX --delete \
  /mnt/cloud/homeserverbkp/ \
  /mnt/backup-inspect/homeserverbkp/
```

The external HDD should then be disconnected/unmounted and stored separately.

# 13. Recommended External-Disk Routine

The external HDD is intended as the **offline/physically separate backup**.

Routine:

```text
1. Connect external HDD
2. Mount it at /mnt/backup-inspect
3. Verify mount
4. Run latest automated backup manually if desired
5. rsync homeserverbkp
6. Verify copy
7. Unmount HDD
8. Store HDD separately
```

Unmount:

```bash
sudo umount /mnt/backup-inspect
```

Verify:

```bash
findmnt /mnt/backup-inspect
```

No output means it is no longer mounted.

# 14. Disaster Recovery Strategy

There are two different levels of disaster.

## Scenario A — Application/configuration problem

Ubuntu is still functioning.

Use the Restic repository to restore the affected configuration.

For example:

```text
/opt/stacks
```

or:

```text
/home/kiran/docker-data/jellyfin/config
```

Do **not** immediately restore everything.

First identify the affected service and restore only the required configuration.

---

# 15. Scenario B — Complete Homeserver Failure

If the NVMe/OS drive fails:

```text
New Ubuntu Server installation
        ↓
Install required packages
        ↓
Install Docker
        ↓
Install Restic
        ↓
Recover Restic repository
        ↓
Restore configuration
        ↓
Restore database dumps
        ↓
Restore application data
        ↓
Start Docker services
        ↓
Verify services
```

The external HDD is critical here.

# 32. Application Data vs Configuration

An extremely important distinction:

### Configuration/database backup

The Restic backup currently protects the information required to reconstruct the services.

### Large media/data

The following are **not intended to be duplicated inside this Restic repository**:

```text
/mnt/media
/mnt/cloud/immich
/mnt/cloud/Seafile
/mnt/cloud/tutorials
```

These contain large amounts of actual user/media data.

They need their **own data-backup strategy**.

Current `/mnt/cloud` contents include approximately:

```text
Seafile       ~81 GB
tutorials     ~191 GB
immich        ~210 GB
```

Therefore the Restic repository is primarily the **homeserver configuration + recovery backup**, not a complete backup of all multimedia/user data.

# 37. Recovery Priority

If the homeserver completely dies, recover in this order:

```text
1. Ubuntu Server
2. Network
3. Docker
4. Restic
5. Restic password
6. /opt/stacks
7. Docker application configuration
8. Database dumps
9. /mnt/cloud data
10. /mnt/media data
11. HTTPS/certificates
12. DNS/Tailscale
13. Start and verify services
14. Re-enable automated backup
15. Reconnect external backup routine
```

The **Restic repository + password** are the foundation of the recovery process.

## 38. Backup Philosophy

The homeserver backup system follows three principles:

**1. Automated local backup**

```text
Homeserver → /mnt/cloud/homeserverbkp
```

Daily through systemd.

**2. Separate physical copy**

```text
/mnt/cloud/homeserverbkp
        ↓
External HDD
```

Copied manually with `rsync`.

**3. Test the backup**

A backup is not considered reliable merely because Restic reports a successful snapshot.

We have already tested:

* Restic snapshot creation
* Restic repository integrity
* Full restore to a temporary directory
* Immich PostgreSQL dump validity
* BookOrbit PostgreSQL dump validity
* Seafile MariaDB dump validity
* Restoration of `/opt/stacks`
* Restoration of certificates

This should be repeated periodically.
